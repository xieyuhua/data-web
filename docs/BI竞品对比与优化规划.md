# 青衡 BI · 市场竞争分析与优化规划

> 文档版本：v1.0 ｜ 更新时间：2026-11-14 ｜ 对应代码：`master` 分支（26k+ 行 Vue / 12.8k 行 Go）
>
> 本文用于回答三个问题：**我们和市面上的 BI 差在哪、我们的差异化优势是什么、下一步该补什么**。
> 结论先行，对比在后，落地清单与路线图在文末。

---

## 0. 结论摘要（TL;DR）

| 判断 | 说明 |
|---|---|
| **我们不是通用型自助 BI** | 不做「人人拖拽出报表」，而是做「**多层级组织经营分析平台**」：集团 → 大区 → 区域 → 门店的四级口径、目标达成、按人推送，出厂即用。 |
| **最强壁垒：组织穿透** | 一条 SQL 通过 `{{org_scope}}` 注入权限，**看板 / 下钻 / 趋势 / 导出 / 分享 / 推送 / 目标达成** 全链路同一套数据边界，配置成本接近 0；Tableau / Power BI / Superset 需要逐套配置 RLS、数据集权限或网关规则。 |
| **第二壁垒：把「看完之后」也做了** | 定时把销售卡片推到企业微信 / 微信，每个接收人拿到的是**带自己数据范围快照的授权链接**；通用 BI 通常要再叠一个自动化/集成产品。 |
| **最大短板：分析深度与自助能力** | 没有语义层与自助拖拽建模、没有抽取式 OLAP 引擎、没有行列级字段脱敏、没有 AI 问答、图表类型偏少。 |
| **理性定位** | 100~2000 人、门店/区域/大区强管控、以「看数与追目标」为主的零售/连锁/快消企业：**我们比商业 BI 更省事、比开源 BI 更省人力**；数据分析师主导的探索式分析场景，仍应保留 FineBI / Power BI / Tableau。 |

## 3. 我们的优势（可对外讲的 7 条）

### 3.1 权限是「长在骨子里」的，不是后配的

- 角色三种数据范围：`all`（全量）、`own_org_tree`（本组织及下级）、`own_org`（仅本组织）。
- 查询时由 `sqlguard` 把 `{{org_scope}}` 展开为组织 ID 白名单，**在数据库层收敛**，前端拿不到越权数据。
- 同一套边界贯穿：看板取数、组织下钻、指标趋势、Excel 导出、分享链接、定时推送、目标达成率。
- 对比：Power BI 的 RLS 要逐表写 DAX 过滤、FineBI 要逐数据集配行列权限、Superset 靠 RLS 规则表，**换一张数据集就要重配一次**。

### 3.2 「看完 → 追目标 → 被提醒」闭环

通用 BI 的输出是「图」，我们的输出是「经营动作」：

1. 店长打开首页 → 角色自动落在自己门店 → 看当日销售额 / 毛利 / 达成率；
2. 大区经理点开「华东大区」→ 看到下属区域汇总 → 再点区域看门店；
3. 每天 9:00 企业微信收到文本卡片 → 点击直达**带本人数据范围**的授权看板。

### 3.3 推送比商业 BI 更「中国化」

- 通道：企业微信应用消息（`text` / `textcard`）、群机器人（`markdown`）、微信公众号模板消息。
- 每个接收人独立生成授权链接（范围快照 + 有效期 + 次数上限），**转发即失效边界外泄风险**。
- 模板与样式在后台可视化配置，不用改代码；推送记录可重试、可追溯。

### 3.4 分享链接天生带权限

「复制链接发给店长」在多数 BI 里意味着开账号或开 Viewer 席位；我们给的是**免登录、限时、限次、限范围**的公共链接，并且访问本身进审计。

### 3.5 二开成本低

- 后端 12.8k 行 Go，严格 `handler → service → repository → model`，service 不依赖 Gin，可直接单测（已有 sqlguard / drill / push / wecom 等 10+ 测试文件）。
- 前端 12k 行 Vue3，组件边界清晰（`ChartRenderer` / `WidgetRenderer` / `NumText`）。
- 单二进制 + 单端口 8486，SQLite 零依赖，`docker-compose` 一把起。
- 对比：FineBI 二开是 Java 插件 + 闭源包；Superset 二开会踩 Flask-AppBuilder 权限模型；本平台改一个指标就是改一段 SQL。

### 3.6 阅读一致性做得细

- 全站数字 `NumText`：点击 `10,000` ⇄ `1万`，等宽数字不跳动；
- 单行数据自动表格、多行自动图表，可手动切换并记住默认；
- 图表元素点击 = 联动筛选；KPI 数字点击 = 看最近 7/30/90 天趋势。

### 3.7 安全基线齐

只读 SQL 校验（禁注释/多语句/写操作）、筛选值白名单 + 字面量转义、DSN AES-GCM 加密、企微 Secret 只掩码回显、JWT 鉴权、审计日志 Token 脱敏、分享可撤销。

## 5. 差异化定位：谁该用我们，谁不该

**推荐用**

- 连锁零售 / 餐饮 / 快消 / 医药连锁：门店多、层级深、店长不熟悉 BI 工具；
- 已有 ERP/POS/中台，但缺「按组织切片的经营看板 + 目标追踪 + 企微提醒」；
- 有 1~2 名开发，希望**自己维护**而不是年年交许可费；
- 数据敏感，要求私有化、免登录分享可控、审计可查。

**不建议单独用**

- 数据分析师主导的探索式分析（异常归因、自由组合维度）→ 建议 FineBI / Power BI / Tableau；
- 十亿行级明细秒级响应 → 需要 ClickHouse/Doris + 语义层；
- 需要 AI 生成报表、自动洞察 → 商业 BI 的 Copilot 更成熟。

> 实践建议：**本平台做「经营层」，商业 BI 做「分析师层」**，两边共用同一个数仓/数据集，不冲突。

## 6. 优化路线图

### P0（1~2 周，投入产出比最高）

| 项 | 方案 | 收益 |
|---|---|---|
| **导出可对账**（本轮已做） | Excel 增加「导出说明」工作表：统计周期、数据范围、筛选条件、导出人、导出时间、组件清单 | 财务/审计对账不再问「这份表什么口径」 |
| **异常可自愈**（本轮已做） | 组件查询失败显示「重试」；错误信息区分权限/超时/SQL | 减少「刷新一下就好了」的工单 |
| 列级脱敏 | 数据集字段配置 `mask`（手机号/金额/身份证），按角色开关 | 补齐合规短板，替代 Excel 手工处理 |
| 慢查询与数据源健康 | 记录每次查询耗时/行数，后台出「慢查询 Top20」 | 提前发现源库瓶颈 |
| 推送失败告警 | 推送记录失败率超阈值 → 给管理员推一条企微消息 | 避免「以为发了其实没发」 |

### P1（1~2 月）

| 项 | 方案 | 收益 |
|---|---|---|
| 语义层（轻量） | 数据集上定义维度/度量/默认聚合，看板配置用字段名而非裸 SQL | 业务可自助换维度，减少改 SQL |
| 组件类型扩充 | 地图（区域/门店热力）、漏斗、瀑布、进度条、指标对比卡 | 覆盖零售常用分析范式 |
| 图表交互增强 | 图表内框选过滤、图例点击隐藏、坐标轴对数、双轴组合图 | 接近商业 BI 手感 |
| 看板版本与回滚 | 每次发布存快照，可对比/回滚 | 降低误操作成本 |
| 多通道推送 | 钉钉机器人、飞书机器人、邮件（SMTP） | 覆盖更多组织 |
| 明细导出异步化 | 超过 5 万行走后台任务 + 下载中心 | 突破 2000 行限制 |

### P2（3~6 月）

| 项 | 方案 | 收益 |
|---|---|---|
| 抽取加速层 | 定时把数据集落到 SQLite/DuckDB/ClickHouse，看板查加速层 | 明细级秒开，降低源库压力 |
| AI 助手 | 「本月华东为什么下滑」→ 自动拆维度 + 生成结论（接大模型 + 指标元数据） | 对标 Copilot / Tableau Pulse |
| 血缘与影响分析 | 数据集 → 看板 → 推送的引用图 | 改字段前知道影响谁 |
| 审批与订阅中心 | 看板申请、发布审批、个人订阅（每日/每周） | 大企业治理必需 |
| 多语言 / 深色主题 | i18n + CSS 变量主题 | 跨境与夜班场景 |

## 8. 运行与容量基线建议

| 项 | 当前值 | 建议 |
|---|---|---|
| 单次查询行数上限 | 2000 行 | 明细分析场景提到 5000，并配合异步导出 |
| 查询超时 | 10s | 保留；超时提示改为「缩小时间范围或联系管理员加索引」 |
| 结果缓存 TTL | 20s | 门店类看板可调到 60s；手动刷新始终穿透 |
| 平台库 | SQLite | 并发 > 50 或多人同时导出时切换 MySQL 8（`DB_DRIVER=mysql`） |
| 数据源账号 | 只读 | 生产强制「只读账号 + 仅授权业务视图」 |
| 分享链接 | 有效期 + 次数 | 对外分享默认 7 天 / 20 次，内部 30 天 |
| 审计留存 | 默认全量 | 建议保留 180 天，敏感操作（导出/分享）永久 |

## 9. 风险与合规清单

1. **越权风险**：新增取数入口必须走 `ScopeService.Resolve` + `sqlguard`，禁止前端传组织 ID 直查。
2. **注入风险**：所有筛选值只能通过 `{{filter:key}}` / `{{filter_in:key}}` 注入，禁止字符串拼接 SQL。
3. **泄露风险**：分享链接即凭证，必须限时/限次/可撤销；日志中 Token 已脱敏。
4. **凭证管理**：企业微信 Secret、数据源 DSN 加密存储，接口回显只给掩码。
5. **数据口径**：导出必须带说明页（本轮已实现），避免「同名不同口径」。
